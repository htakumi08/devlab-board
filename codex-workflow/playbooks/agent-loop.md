# 機能開発ループ

この手順は、ユーザーが依頼した機能の完了まで同じ作業を継続するための入口である。モデル名は現在利用可能な `gpt-6.1-sol` と `gpt-6-luna` を使う。モデルを指定できない実行環境では、実際のモデルを明示し、変更したふりをしない。

| 担当 | モデル | 成果物 |
| --- | --- | --- |
| 統合、サブエージェント設定、要件、設計、アーキテクチャ、レビュー | `gpt-6.1-sol` | 受け入れ条件、設計判断、担当境界、レビュー結果 |
| 実装、定型更新、合意済みテストケースの Playwright E2E | `gpt-6-luna` | コード、対象テスト、実行結果 |

## 一周の流れ

1. Sol が依頼、現行コード、関連 docs、作業ツリーを確認し、利用者の操作、画面・API・DB・インフラの境界、正常・異常系、観測可能な受け入れ条件を決める。不明点は作業を止めるものだけ確認する。複数領域の変更では [計画プレイブック](./plan.md) を使う。
2. Sol が変更するファイル群、担当者、依存順、検証方法を決める。単純な一領域の作業ではサブエージェントを増やさない。
3. Luna が担当ファイルだけを実装する。テストケースが決まっている E2E は Luna が Playwright で作成・実行する。仕様やアーキテクチャ判断が新たに必要なら Sol に戻す。
4. Sol が差分と証拠を確認する。[検証プレイブック](./verify.md) の対象コマンド、必要な DB 統合テスト、E2E、API 契約、docs の整合を評価する。レビュー観点は [コードレビュープレイブック](./code-review.md) に従う。
5. 受け入れ条件を満たさない場合は、失敗した条件と再現方法を一つずつ Luna に返して修正する。設計が原因なら Sol が設計を更新してから戻す。修正後は影響範囲の検証を再実行する。
6. 全条件が通ったら結果を報告する。環境障害などで実行できない確認は、実行していない事実、理由、残リスクを明示して引き継ぐ。

## サブエージェントへ渡す最小情報

- 目的と受け入れ条件、関連する既存契約への path。
- 担当 role (`roles/`)、触ってよい path、触ってはいけない共有ファイル。
- 対象テスト・E2E ケース、実行コマンド、報告する結果。
- 既存の未コミット差分を保持する指示。

起動時はモデルを明示する。Sol は要件・設計・レビュー、Luna は実装・定型作業・指定済み E2E に割り当てる。独立したファイルだけ並列にし、同じファイルへの同時編集を避ける。同じ修正担当には新しいエージェントを増やさず、可能なら既存エージェントへ追依頼する。

## トークンと継続

- 読むファイルは対象機能、契約、関連テストから絞る。大きなログは失敗箇所を先に見る。
- ケース一覧と検証結果を短く残し、次の反復では差分と未達条件だけを渡す。既知の事実を毎回調べ直さない。
- 同じ失敗が繰り返される場合は、再実行を重ねず Sol が仮説と検証方法を変える。
- 受け入れ条件を満たすまで作業を続ける。ユーザー入力や外部環境が必要な場合は、独立した作業を先に進めてから具体的な停止理由を伝える。
- ローカルの反復と別セッションでの継続は区別する。自動再開を設定していない場合、次の依頼時は受け入れ条件・未達・最後の検証結果を読み直して再開する。
