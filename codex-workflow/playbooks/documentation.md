# ドキュメント運用プレイブック

## 使う場面

- 新しい docs を作るとき。
- 既存 docs を更新するとき。
- 要件、設計、アーキテクチャ、API、DB、Runbook、ADR を整理するとき。
- 図解や目次、更新履歴を整えるとき。

## 作成フロー

1. 参照元を確認する。
   - ユーザーの最新要望
   - 既存 docs
   - `AGENTS.md`
   - 関連する `codex-workflow/rules/`
2. ドキュメントの目的と読者を決める。
3. 正式 docs か、`docs/api/` の API 叩き台か、`docs/implementation/` の実装メモかを決める。
4. 長くなる docs では frontmatter、更新履歴、番号付き見出し、目次を用意する。
5. 複雑な流れは Mermaid または text 図で図解する。
6. `## 要確認・ヒアリング項目` を最後に置く。
7. リンク、見出し番号、日付、ファイル名を確認する。

## implementation docs の扱い

`docs/implementation/` は、実装後の補足メモを管理運用する場所です。

置くもの:

- どの方針で実装したか。
- どのファイルに何を加えたか。
- どのテストや build で検証したか。
- その実装で置いた前提や MVP 上の割り切り。

命名:

```text
docs/implementation/{topic}-implementation.md
```

注意:

- API 設計の叩き台は `docs/api/` に置く。
- 実装後の変更整理メモは `docs/implementation/` に置く。
- 同じ topic で設計案と実装メモがある場合、役割を混ぜない。

## 更新フロー

1. 変更対象の章を確認する。
2. 関連 docs に矛盾が出ないか確認する。
3. 本文を更新する。
4. 更新履歴がある docs では 1 行追加する。
5. 番号付き `##` 見出しが増減した場合は `## 目次` を更新する。
6. 図解と本文が矛盾していないか確認する。
7. 未決定事項は `## 要確認・ヒアリング項目` へ移す。

## 図解ルール

次の場合は図解を検討します。

- 3 つ以上のコンポーネントが関係する。
- 非同期処理や再試行がある。
- 状態が 3 つ以上ある。
- 文章だけだとデータの流れが分かりにくい。
- UI の概念を共有したい。

使い分け:

- アーキテクチャ: `flowchart`
- API / 非同期処理: `sequenceDiagram`
- 状態遷移: `stateDiagram-v2`
- UI ラフ: `text`

## 完了条件

- docs の置き場所が目的に合っている。
- 図解が必要な複雑箇所に図がある。
- 未決定事項が要確認として集約されている。
- 変更内容をユーザーへ簡潔に説明できる。
