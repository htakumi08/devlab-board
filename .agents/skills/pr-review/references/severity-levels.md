# レビュー指摘の重大度

指摘には `大`、`中`、`小` のいずれかを付ける。変更量や修正工数ではなく、問題が現実に起きた場合の影響で判定する。

## 判定基準

| 重大度 | 基準 | 代表例 |
| --- | --- | --- |
| 大 | merge やリリースを止めるべき問題。主要機能が利用不能になる、認証・認可を回避できる、機密情報が露出する、データ消失・破壊・他ユーザーへの越境が起きる、または復旧困難な本番障害につながる | ログイン不能、認可漏れ、secret の commit、破壊的 migration、主要 API の常時失敗 |
| 中 | 利用者や運用に明確な実害があるが、条件や範囲が限定される、回避策がある、または復旧可能な問題。仕様逸脱、限定条件での機能不全、回復可能な不整合、現実的な性能・運用悪化を含む | 一部入力で誤動作、error 時だけ不正な状態、pagination 不足による性能低下、重要分岐の test gap |
| 小 | 現在の機能・セキュリティ・データ整合性を壊さない局所的な問題。軽微な UI・ログ・docs の不整合や、将来の変更を難しくする限定的な保守性問題 | 誤解を招く文言、軽微な docs ずれ、重複した定数、限定的な可読性低下 |

## 判定手順

1. 問題が発生する具体的な入力、状態、操作、環境を示す。
2. 発生時に壊れる挙動、データ、権限、運用を特定する。
3. 到達可能性、影響を受ける範囲、回避策、復旧可能性を確認する。
4. 根拠で到達可能と判断できる最も深刻な影響に対応する重大度を付ける。
5. 同じ原因の指摘はまとめ、異なる影響は分ける。

## 運用ルール

- 重大度からGitHubの `APPROVE` や `REQUEST_CHANGES` を自動選択しない。
- 確度と重大度を混同しない。未確認の前提がある場合は `要確認` と書き、その前提が成立した場合の影響で重大度を付ける。
- test 不足だけを理由に自動で `大` にしない。未検出になり得る具体的な回帰の影響で判定する。
- 修正が簡単でも影響が大きければ `大`、修正が難しくても実害が小さければ `小` とする。
- 好み、任意の改善、根拠のない将来懸念は指摘にしない。
- 複数の重大度が考えられる場合は、根拠で到達可能と判断できる最も深刻な影響を採用する。根拠のない仮想的な連鎖では重大度を引き上げない。
