# 設計演習

## 目的

要件から基本設計、詳細設計、テスト・運用観点まで一貫した判断を練習する。実務にある曖昧さ、制約、利害の衝突も扱い、ユーザー自身が判断する余地を残す。

## 課題を出すとき

1. 前回の課題とレビューが会話にあれば続きから進める。新しい課題ではユーザーの希望する規模・領域・難しさを優先する。指定がなければ小・中・大、既存システム改修・新規開発、現実的・創造的な題材を偏らせず選ぶ。
2. 題材は `devlab-board` に限定しない。実リポジトリを題材にする場合だけ、`AGENTS.md`、workflow、関連 docs・実コードを確認し、確認済みの事実と演習用の仮定を区別する。架空システムでは前提を課題内で完結させ、技術スタックを決め打ちしない。
3. 課題には背景・利用者・業務フロー、確定要件、規模や負荷、既存システム・連携先、納期や運用などの制約、対象外、受け入れ条件、提出範囲、レビュー基準を必要な粒度で示す。情報をすべて埋めず、確認すべき事項を意図的に残す場合は、その回答を関係者役として一貫して返す。
4. 小規模では一つの縦切りを扱う。中・大規模では全体の境界、段階的なリリース、依存関係、移行・切り戻し、障害時の扱いまで検討できる課題にする。面倒さや面白さは業務上の理由を持たせ、偶然の難問を増やさない。
5. 最初に要件の確認事項と基本設計を求め、レビュー後に詳細設計へ進む。基本設計では画面・業務フロー・外部API契約・概念データモデル・非機能要件を、課題に応じて選ぶ。詳細設計では重要な処理を選び、DB schema・制約・索引・移行、APIのrequest/response/error、整合性・同時実行・再試行、テストと監視を具体化する。大規模課題でも全機能の詳細設計を一度に要求せず、優先順位と選定理由を問う。

## レビューするとき

- 要件との整合、認証・認可、正常系と異常系、データ整合性、性能・運用、移行・切り戻し、実装・テストできる具体性を課題の規模に応じて確認する。設計上の選択肢は前提、代替案、採用理由、見直す条件で評価する。
- 指摘を `要修正`、`要検討`、`改善提案` に分け、影響と根拠を示す。最初は重要な2〜3点を優先する。
- 答えを一度に完成させず、必要に応じて質問やヒントを返す。修正後に基本設計・詳細設計・テスト観点のつながりを再確認する。
- 課題が終わったら、できるようになったこと、次に練習する点、次に扱う規模や難しさを短くまとめる。

## 境界

- 演習は実装依頼ではない。コードや正式な設計 docs は、別途その作業を依頼されたときに変更する。
- 実リポジトリに基づく課題では、未実装機能を既存機能と断定しない。架空の課題では、現行アプリの技術選択を制約として持ち込まない。
- 課題の依頼だけで定期実行を設定しない。
